## 关键验证：重启不再踢掉自己

这一项是 v1.5.5 最有说服力的证据，因为它同时否掉了两个之前的假设。

| 项目 | 值 |
|---|---|
| 会话建立 | 09:10:14（`session_origin = reauth-password`） |
| 重启时间 | 13:27:51 |
| 重启后 `session_state` | **`rt`** |
| `session_end_reason` | **`None`**（未测试 = 正常运行） |
| `refresh_attempts` | **`[]`**（一次续期都没触发） |
| `token_expires_in_seconds` | 约 **28.8 天** |
| `session_held_by_socket` | **True** |

对比历史：

| 场景 | 重启后结果 |
|---|---|
| 21:21 验证 → 21:27 重启（App 未登录，无 socket） | **重启那一秒就 401** |
| 09:10 验证 + socket 长连接 → 13:27 重启 | **`rt`，零续期，有效期 28.8 天** |

变量差异只有一个：**会话是否被长连接持续使用**。这印证了 v1.5.5 把实时推送设为默认开启的判断，
也再次说明 v1.5.4「rt 被过期 at 挡住」的解释不成立 —— 真正的分水岭是会话有没有人用。

## 仍未解决（也不是集成能解决的）

App 一旦登录，这个会话仍会作废。v1.5.5 能做的是：

1. 让集成自己不要把自己踢掉（本轮已验证）；
2. 会话真的被踢时，把原因写清楚（`session_end_reason = session_superseded` + 中文提示）；
3. 提供**共享账号**入口，走官方推荐的双账号路线，这才是"App 与集成同时在线"的正解。

## 下一步需要用户做的选择

| 你的取舍 | 做法 |
|---|---|
| 只要 HA 自动化，手机 App 可以退 | 什么都不用做，当前状态已经是这样 |
| 两边都要用 | 在 OKP App 里把设备分享给第二个账号，然后在 HA 里「添加集成 → OKP 扫地机器人 → 共享账号」用副账号登录 |
| 账号同时被易微联等其他 CoolKit 应用使用 | 配置 → 选项 → 填那个应用的 appid |
