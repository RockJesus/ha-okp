# v1.6.5 验证报告：entity_scope 根因

## 结论先行

「多账号登录时，不显示设备」的**真正根因**是 `entity_scope()` 从 v1.6.2 起就从未生效——
它读取 `entry.hass`，而 Home Assistant 的 `ConfigEntry` **没有 `hass` 属性**。

v1.6.5 已修复并部署验证：两个条目现在拿到**不同的** `entity_scope`，
协调器各为 1 个，会话状态 `rt`，realtime `connected`。

## 证据链

### 1. 症状

升级前 `refresh_session` 返回（v1.6.4 运行时）：

| 条目 | scope | coordinator | 实体数 |
|---|---|---|---|
| 主账号 | `None` | `None` | 34 |
| 副账号 | `None` | `None` | **0** |

字段全为 `None` 是因为 v1.6.3 引入的 `CONF_ACCOUNT` 未导入，
`refresh_session` 直接抛 `name 'CONF_ACCOUNT' is not defined`。

### 2. 根因定位

HA 核心 `homeassistant/config_entries.py` 中 `class ConfigEntry` 的类体
（第 435 行起）声明了 `entry_id`、`domain`、`title`、`data`、`created_at` 等属性，
**没有 `hass`**。所有 `hass` 出现处都是**方法参数**：

```python
def async_setup(self, hass: HomeAssistant) -> None:   # 第 741 行
def async_unload(self, hass: HomeAssistant, *_) -> None:  # 第 758 行
```

而 v1.6.2 的实现是：

```python
entries = entry.hass.config_entries.async_entries(DOMAIN) \
          if getattr(entry, "hass", None) is not None else []
```

`getattr(entry, "hass", None)` **恒为 `None`** → `entries` 恒为空 →
`ordered` 为空 → 函数对**每一个条目**都返回 `""`。

结果：两个账号产出的 `unique_id` 完全相同
（`okp_cloud_100258a68a`、`okp_cloud_100258a68a_work_state` …），
HA 按 unique_id 去重，第二份被静默丢弃，只在日志留一行：

```
Platform okp_cloud does not generate unique IDs. ID okp_cloud_100258a68a already exists - ignoring vacuum.sao_di_ji_qi_ren
```

### 3. 为什么排查绕了远路

| 版本 | 声称 | 实际情况 |
|---|---|---|
| v1.6.2 | 修好 unique_id 撞车 | `entity_scope` 恒返回 `""`，**修复从未生效** |
| v1.6.3 | 加诊断字段 | `CONF_ACCOUNT` 未导入，服务**必崩**，反而掩盖线索 |
| v1.6.4 | 修设备发现 | 代码正确，但**装不上**（manifest 曾被写成 0 字节） |

另外 `update` 实体长期谎报 `installed = v1.6.2`，实际运行的是 v1.5.5 / v1.6.0。
原因是 HACS 走 `ghrp2.hacs.vip` 镜像，**单文件超时 60 秒即失败**
（日志 `Tries left 14`），安装从未真正落地。

## 修复

`entity_scope` 签名改为显式接收 `hass`：

```python
def entity_scope(hass: HomeAssistant | None, entry: ConfigEntry | None) -> str:
    if hass is None or entry is None:
        return ""
    entries = [e for e in hass.config_entries.async_entries(DOMAIN) if e.domain == DOMAIN]
    def _created(e): ...   # created_at 是 datetime，需归一为 float
    ordered = sorted(entries, key=lambda e: (_created(e), e.entry_id))
    if not ordered or ordered[0].entry_id == entry.entry_id:
        return ""
    return f"_{entry.entry_id[-6:]}"
```

六个平台（vacuum / sensor / select / switch / button / camera）与
`refresh_session` 诊断共 7 处调用全部改为 `entity_scope(hass, entry)`。

`created_at` 在 HA 当前版本是 `datetime` 对象，旧条目可能缺失，
因此做类型归一，避免 `TypeError: '<' not supported`。

## 部署验证（HA 实测）

v1.6.5 安装并重启后：

| 条目 | scope | coordinator | has_coordinator |
|---|---|---|---|
| `01M6GJ1WVDWPZSK1HGT762MSHS` | `''` | 1 | True |
| `01M6GJWJPHQQSX0A19X1D1PZV0` | `'_D1PZV0'` | 1 | True |

`refresh_session` 不再抛异常，诊断字段完整可读。

## 遗留：副账号需要在 HA 侧重新配置一次

修复的是**代码**，但副账号条目是**用旧逻辑创建的**，
其设备列表与实体需在正确 scope 下重新生成。

验证过程中还观察到：HA 重启后出现 `session was taken over`
（手机 App 同时登录同一账号），以及配置条目被重建
（`01M6GSZTS12TNY9EHYFS29HSSC`，创建于 21:36:14）。

因此下一步需要在 HA 界面里，用副账号重新走一次「添加集成 → 共享账号」，
让副账号拿到 `<entry_id>` 后缀的独立实体组。

主账号不受影响：`entity_scope` 对最早创建的条目返回 `''`，
`vacuum.sao_di_ji_qi_ren` 等历史实体 ID、自动化、仪表盘全部保持原样。
