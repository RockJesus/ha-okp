# App 登录干扰实测：推翻"实时推送是主因"

> 2026-11-02 20:28~20:37 实测。这次有了可控的对照条件，结论必须修正。

## 实测时间线

| 时间 | 事件 | 证据 |
|---|---|---|
| 20:28:44 | 用户完成**重新验证**，拿到新 at/rt | `session_started_at = 20:28:44`，`session_origin = reauth-password`，`rt_issued_at = 20:28:44` |
| 20:30:25 | 仍能正常取数 | `battery = 100`、`work_state = 7`，`last_updated = 20:30:25` |
| 20:36:26 | 云端拒绝 | `401 cannot found access token info`，`last_rt_probe_result = rejected` |
| 20:37 | 查询 | `session_state = stale`，`has_refresh_token = True` |

**从验证成功到会话被销毁，间隔 8 分钟。**

## 关键反证：实时推送当时是关闭的

```
sensor.ke_ting_okp_k5_ultra_realtime_push = disabled
  note: "realtime channel not started"
  device_pushes: 0
冷却项 options = null   → 走默认值
const.py: CONF_REALTIME_DEFAULT = False
```

**`realtime = None`，socket 从未建立。**

这直接推翻了 v1.5.3 的单一因果假设：会话在 8 分钟内失效，而当时**没有任何 WebSocket 连接**。
"实时推送与轮询互抢"最多是一个**次要放大器**，不是这次失效的原因。

## 修正后的判断

v1.5.3 修的机制本身是真实的（两个写者共用一个单会话 slot 确实会互相顶），
但它**解释不了"没有 socket 也会 8 分钟失效"**。

结合 `session_origin = reauth-password` 与 8 分钟窗口，最符合证据的解释是：

> **用户在 20:28 重新验证时，手机 App 正登录着。**
> 密码登录会新建一个会话；随后 App 侧任意一次请求（刷新 token、建立推送、切换页面触发的 token 续期）
> 又会新建/替换会话，把集成刚拿到的这套凭据作废。
> 8 分钟正好是 App 前台活跃时的典型续期间隔。

也就是说：**问题不在集成内部，而在"两个客户端共用一个账号 slot"这个前提本身。**
集成这边已经做了能做的（rt 续期、静默自愈、会话归属标记），但厂商只给一个 slot，怎么调度都会有一方被顶。

## 该怎么验证（决定性实验）

这次的条件刚好是理想的对照，只要补一个动作就能定论：

1. **完全退出 App**（从最近任务里划掉，不是切后台）
2. 在 HA 里重新验证一次，记下 `session_started_at`
3. **接下来 20 分钟不要打开 App**
4. 观察 `session_state` 与 `token_age_seconds`

| 结果 | 判定 |
|---|---|
| 20 分钟以上保持 `rt` | **确认是 App 干扰**，集成无 bug。App 只要登录就会顶掉集成 |
| 仍然 10 分钟内变 `stale` | 集成侧还有问题，需要继续挖（此时 socket 也没开，范围极小） |

## 我需要更正的话

上一轮我把"引入实时推送之后才出问题"当成了因果证据，并据此断定是 socket 与轮询互抢，
还给了一个打包票式的结论（"如果 v1.5.3 部署后重启仍然失效，几乎可以确定是 App 顶号"）。

**这次数据显示这个推断不成立**：socket 根本没开，会话照样 8 分钟就没了。
真实原因更可能是 App 与集成同时在线。我应该在做完这个对照实验之后再下结论，而不是先给结论再找证据。

## v1.5.3 的价值（保留）

即使不是主因，这些改动仍然是对的：

- 会话归属标记：socket 在线时轮询不再轮换 token，避免"自己把自己踢掉"
- 到期前主动交还：续期与登记错开时序
- `refresh_session force` 不再强行轮换
- 心跳失败不再静默

这些在**用户真的开启实时推送**时是必要的保护。但请不要指望它解决 App 同时登录的问题。

## 实验结果（21:13 读取）

对照实验完成，判定明确。

### 数据

| 项目 | 值 |
|---|---|
| 重新验证时间 | **20:39:26**（`session_started_at` / `rt_issued_at`） |
| 查询时间 | 21:13:27 |
| **稳定时长** | **34 分钟** |
| `session_state` | **`rt`** |
| `token_expires_in_seconds` | 约 **29 天** |
| `error` | `None` |
| `last_poll_at` | 21:12:14（轮询正常） |
| App 状态 | 完全退出，未打开 |

### 判定

**✅ 确认是 App 干扰，集成自身无 bug。**

同样一套代码、同样一次重新验证：

| 场景 | 结果 |
|---|---|
| 20:28 验证时 **App 登录着** | 8 分钟后变 `stale`，rt 也被拒 |
| 20:39 验证时 **App 已退出** | 34 分钟稳定 `rt`，有效期 29 天 |

变量只有一个：App 是否在线。结论清晰。

### 最终定性

1. **厂商限制**：OKP/CoolKit 账号同一时刻只允许一个会话。App 登录 → 集成被顶；集成重新验证 → App 被顶。这是硬约束，集成层无法绕过。
2. **v1.5.3 修的问题**是真实的但非主因：它解决"实时推送开启时 socket 与轮询互抢"，防止集成**自己把自己**踢掉。
3. **v1.5.0~v1.5.2 的排查方向有偏**：一直在查"令牌有没有存对"，而真实变量是"谁在线"。

### 使用建议

| 需求 | 做法 |
|---|---|
| 以 HA 自动化为主 | App 不要保持登录；需要看地图时临时登录，用完退出，再回 HA 重新验证 |
| 两者都要 | 无法稳定共存，只能接受"谁最后登录谁生效" |
| 只想要 App | 卸载集成，避免每天互相踢 |

### 遗留观察项

`battery` 等实体的 `last_updated` 停在 20:42，而 `last_poll_at` 是 21:12 —— 这是因为**值没变化时 HA 不更新 `last_updated`**，不是轮询停止。
判断轮询是否正常，应看 `last_poll_at`，不要看实体时间戳。

建议继续观察 24 小时，确认无自发失效。
